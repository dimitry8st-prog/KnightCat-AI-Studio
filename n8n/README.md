# Запуск минимального n8n workflow

Файл для импорта:

- `workflows/knightcat-minimal-telegram.json`

## Что уже реализовано

```text
Telegram message
→ авторизация пользователя
→ проверка входа
→ OpenRouter
→ разбор и проверка JSON
→ сохранение черновика
→ предпросмотр в Telegram
→ /approve или /reject
→ публикация одобренной Telegram-версии
→ подтверждение
```

Workflow по умолчанию выключен и не содержит секретов.

## Требования

- n8n с публичным HTTPS URL для Telegram webhook;
- Telegram-бот, созданный через BotFather;
- OpenRouter API key;
- Telegram-канал или чат для публикации;
- бот должен иметь право отправлять сообщения в целевой канал.

## 1. Импорт

1. Откройте n8n.
2. Выберите **Workflows → Import from File**.
3. Импортируйте `knightcat-minimal-telegram.json`.
4. Не активируйте workflow до завершения настройки.

## 2. Telegram credential

Создайте credential типа **Telegram API** с токеном бота.

Выберите его во всех Telegram-узлах:

- Telegram Trigger;
- Send Draft for Approval;
- Send Processing Error;
- Publish to Telegram;
- Confirm Publication;
- Send Approval Error;
- Confirm Rejection;
- Send Help or Access Error.

Плейсхолдер `REPLACE_TELEGRAM_CREDENTIAL_ID` не является секретом и должен быть заменён выбором credential в интерфейсе n8n.

## 3. OpenRouter credential

Создайте credential типа **Header Auth**:

| Поле | Значение |
|---|---|
| Name | `Authorization` |
| Value | `Bearer ВАШ_OPENROUTER_API_KEY` |

Выберите его в узле **Generate with OpenRouter**.

Плейсхолдер `REPLACE_OPENROUTER_CREDENTIAL_ID` должен быть заменён через интерфейс.

## 4. Переменные n8n

Создайте переменные проекта:

| Переменная | Обязательность | Пример |
|---|---|---|
| `KNIGHTCAT_ALLOWED_USER_IDS` | обязательно | `123456789` |
| `KNIGHTCAT_PUBLISH_CHAT_ID` | рекомендуется | `@knightcat_test` или `-1001234567890` |
| `KNIGHTCAT_OPENROUTER_MODEL` | необязательно | `openai/gpt-4.1-mini` |
| `KNIGHTCAT_FOOTER` | необязательно | `@your_channel` |
| `KNIGHTCAT_VK_GROUP_ID` | для стены VK | числовой id сообщества, без знака `-` |
| `KNIGHTCAT_VK_COMMUNITY_TOKEN` | для стены VK | ключ сообщества с правом `wall` |
| `KNIGHTCAT_VK_USER_TOKEN` | для фото VK | пользовательский ключ с правом `photos` |

Несколько разрешённых Telegram user ID указываются через запятую.

Ключи ВКонтакте задаются только переменными n8n. В репозиторий и в текст ошибок они не попадают.

Если `KNIGHTCAT_ALLOWED_USER_IDS` не задана, workflow никого не допускает. Если целевой чат не задан, публикация идёт в исходный чат — это удобно только для безопасного теста.

## 5. Первый тест

1. Нажмите **Test workflow** только для проверки получения сообщения.
2. Отправьте боту идею длиннее 10 символов.
3. Убедитесь, что появился черновик с ID.
4. Не используйте ручное выполнение для проверки сохранения черновика.
5. Активируйте workflow.
6. Отправьте новую тестовую идею.
7. Выполните `/reject ID` и убедитесь, что публикации нет.
8. Создайте второй черновик и выполните `/approve ID`.
9. Проверьте ровно одно сообщение в целевом Telegram-канале.
10. Повторите `/approve ID`: второй публикации быть не должно.

## Команды

```text
/approve REQUEST_ID
/reject REQUEST_ID
/vk-resolve REQUEST_ID
/vk-resolve REQUEST_ID POST_ID
/vk-resolve REQUEST_ID absent
/help
```

`/vk-resolve` ничего не публикует. Команда без второго аргумента только сверяет стену. `POST_ID` записывает уже существующую запись после `wall.getById`. `absent` разрешает один новый `/approve` лишь если сверка подтвердила, что записи нет.

Если ID не указан, команда применяется к последнему черновику текущего чата.

## Контроль безопасности

- публикация выполняется только после `/approve`;
- пользователь должен входить в allowlist;
- черновик можно одобрить только из чата, где он создан;
- повторное одобрение опубликованного пакета блокируется;
- API-ключи не хранятся в репозитории;
- HTTP Request повторяется не более трёх раз;
- невалидный ответ модели не публикуется.

## Публикация во ВКонтакте

Одобрение по-прежнему сначала публикует Telegram-версию. Затем контур берёт `platforms.vk.content` и изображение черновика и публикует запись от имени сообщества. Reject эту ветку не вызывает.

Изображение читается из `visual.image.base64`, из бинарного поля `image` или из локального `visual.image.path`. Без изображения `wall.post` не вызывается. Подготовленный, но не опубликованный пост: `n8n/vk/fixtures/test-post.json` и `media/knightcat-content-factory-poster.jpg`.

По документации VK на 11.10.2026:

1. `wall.post` выполняется ключом сообщества: `owner_id=-GROUP_ID`, `from_group=1`. Ключ создаёт администратор: Управление → Дополнительно → Работа с API → Ключи доступа → Создать ключ. Нужно право `wall`. Официальная страница метода отдельно описывает пользовательский ключ Standalone через Implicit Flow; право `wall` для него VK выдаёт только по запросу на devsupport@corp.vk.com. Для записи от имени сообщества используйте ключ сообщества.
2. `photos.getWallUploadServer` и `photos.saveWallPhoto` в документации вызываются пользовательским ключом с правом `photos`. Это право тоже выдаётся поддержкой в исключительных случаях. Ключ сообщества на загрузке фото стены возвращает ошибку 27, даже если в нём отмечено `photos`.
3. Запросы идут на `https://api.vk.ru/method/` с версией `5.131` и заголовком `Authorization: Bearer`. Ключ не добавляется в URL.
4. Вложение имеет вид `photo{owner_id}_{id}` и принимается только если `owner_id` равен `-GROUP_ID`.
5. Параметр `guid` защищает от повтора около часа. Дольше этого контур держит состояние сам. После тайм-аута `wall.post` статус становится `uncertain`: новый пост не отправляется, пока сверка или `/vk-resolve` не определит исход.

Проверка ключей без публикации: задать три переменные в окружении и запустить `node n8n/vk/probe-access.cjs`. Скрипт вызывает только `groups.getTokenPermissions` и `account.getAppPermissions`.

Локальные проверки на заглушках: `node --test n8n/vk/vk-publisher.test.cjs`. Они не создают запись ВКонтакте.

Активный workflow в n8n этим репозиторием не изменялся. Импорт `n8n/workflows/knightcat-minimal-telegram.json` — отдельное решение после одобрения тестового поста.

## Текущие ограничения MVP

1. На вход по-прежнему принимается только текст Telegram. URL, голос и генерация изображения остаются следующей итерацией. Для стены VK изображение должно уже лежать в черновике.
2. Черновики хранятся в workflow static data. Это подходит для одного экземпляра n8n и небольшого пилота, но не заменяет PostgreSQL.
3. В ручном режиме n8n static data может не сохраниться. Полный approval-тест проводится на активном workflow.
4. Одновременное редактирование пакета не поддерживается.
5. Используются текстовые команды вместо inline-кнопок — это уменьшает количество нестабильных деталей в первом вертикальном срезе.
6. Реальные Telegram и VK в репозитории не вызывались: ключей в окружении нет. Проверка VK на заглушках лежит в `n8n/vk/vk-publisher.test.cjs`.

## Условия перехода к следующему этапу

После успешного smoke-теста:

- заменить static data на PostgreSQL;
- добавить inline-кнопки;
- добавить извлечение URL;
- добавить Whisper;
- вынести промпты в управляемые версии;
- подключить генерацию изображения;
- после стабилизации — Blender-модуль для постоянного 3D-маскота.

## Откат

При любой ошибочной публикации:

1. деактивировать workflow;
2. проверить execution по `request_id`;
3. исправить причину;
4. повторить smoke-тест;
5. активировать workflow только после успешной проверки.
