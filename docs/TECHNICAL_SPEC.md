## 1. Назначение документа

Документ определяет требования к MVP контент-завода **KnightCat AI Studio** — управляемого AI-конвейера для подготовки контента из одного источника для пяти социальных платформ.

ТЗ предназначено для разработки, тестирования и приёмки решения на базе n8n. Оно фиксирует границы первой версии, форматы данных, правила работы AI-моделей, обработку ошибок, контроль публикации и измеримые критерии готовности.

---

## 2. Что было улучшено относительно исходной концепции

В исходном описании была понятная идея и общий маршрут данных, но для разработки не хватало следующих элементов:

1. не были разделены MVP и будущие функции;
2. не было обязательного ручного одобрения перед публикацией;
3. отсутствовали точные контракты входных и выходных данных;
4. не были заданы статусы задания, правила повторов и защита от дублей;
5. промпты не описывали работу с неопределённостью, ошибочными источниками и неподтверждёнными фактами;
6. не были определены безопасность, хранение секретов и сроки хранения данных;
7. отсутствовали метрики качества и критерии приёмки;
8. автоматическое изменение промптов по обратной связи создавало риск неконтролируемого ухудшения;
9. список генераторов изображений не содержал правила выбора основного и резервного сервиса;
10. не было предусмотрено безопасное поведение при сбое отдельных API.

В версии 1.1 эти пробелы закрыты.

## 3. Цель проекта

Создать конвейер, который превращает входную идею или материал в проверяемый пакет контента для Telegram, Instagram, X, VK и TikTok.

### 3.1. Пользовательский результат

Пользователь передаёт исходный материал и получает:

- краткий анализ;
- пять адаптированных черновиков;
- заголовок и теги;
- промпт для изображения;
- при наличии подключённого сервиса — варианты изображения;
- единый валидный JSON-пакет;
- кнопки одобрения, возврата на доработку или отклонения;
- подтверждение публикации и ссылку на опубликованный материал.

### 3.2. Бизнес-результат

Сократить ручную подготовку однотипного контента, сохранив контроль человека над фактами, стилем и публикацией.

### 3.3. Гипотеза MVP

Если одну идею автоматически преобразовывать в пять платформенных черновиков и отдавать на удобное ручное одобрение, пользователь сможет готовить контент быстрее без заметного ухудшения качества.

До пилота базовое время ручной подготовки необходимо измерить на тех же десяти идеях. Целевое улучшение устанавливается только после фиксации этой базы.

## 4. Пользователи и роли

| Роль | Права |
|---|---|
| Автор | Отправляет материалы, просматривает результат, запрашивает доработку |
| Редактор | Проверяет факты и стиль, редактирует и одобряет пакет |
| Публикатор | Подтверждает внешнюю публикацию |
| Администратор | Настраивает интеграции, модели, лимиты и доступ |
| Система | Обрабатывает данные только в рамках workflow и выданных разрешений |

В MVP один человек может совмещать роли автора, редактора, публикатора и администратора, но системные права должны оставаться разделёнными.

## 5. Границы MVP

### 5.1. В MVP входит

- вход через Telegram Bot и HTTP Webhook;
- типы входа: текст, URL и голосовое сообщение;
- транскрибация голосовых сообщений;
- извлечение текста из доступной веб-страницы;
- структурированный анализ материала;
- генерация черновиков для пяти платформ;
- генерация промпта для изображения;
- опциональная генерация двух изображений через одного выбранного провайдера;
- проверка JSON Schema и платформенных ограничений;
- ручное одобрение перед любой публикацией;
- публикация одобренного поста в Telegram;
- сохранение задания, версий контента, статусов и ошибок;
- журнал действий;
- базовые метрики времени, стоимости и числа ошибок.

### 5.2. Не входит в MVP

- полностью автономная публикация без подтверждения;
- автоматическая публикация в Instagram, X, VK и TikTok;
- OCR сканов и сложных PDF;
- автоматическое обучение или самостоятельное изменение промптов;
- полноценная CRM;
- сложное планирование календаря публикаций;
- RAG и долговременная память;
- собственное обучение модели;
- многоагентная архитектура.

Эти функции допускаются после успешного пилота и отдельного решения.

## 6. Функциональный поток

```text
Вход
  → Проверка и нормализация
  → Получение текста
  → Анализ источника
  → Генерация пяти черновиков
  → Генерация визуального промпта
  → Детерминированная проверка
  → AI-проверка качества
  → Ручное одобрение
  → Публикация в Telegram
  → Сохранение результата и метрик
```

### 6.1. Статусы задания

`received` → `extracting` → `analyzing` → `generating` → `validating` → `review_required` → `approved` → `publishing` → `published`

Дополнительные статусы:

- `needs_revision`;
- `rejected`;
- `failed_retryable`;
- `failed_final`;
- `cancelled`.

Каждое изменение статуса записывается в журнал с датой, причиной и инициатором.

## 7. Архитектура MVP

| Компонент | Ответственность |
|---|---|
| Telegram Trigger / Webhook | Приём задания |
| Input Normalizer | Единый формат входа, проверка размера и типа |
| Source Extractor | Транскрибация или извлечение текста по URL |
| Analysis Service | Структурированный анализ источника |
| Content Generator | Пять платформенных версий |
| Visual Prompt Generator | Промпт и короткая надпись для изображения |
| Image Provider Adapter | Вызов выбранного сервиса генерации |
| Validation Layer | JSON Schema, длина, обязательные поля, запрещённые элементы |
| Quality Reviewer | Проверка фактов, соответствия источнику и стилю |
| Approval Gate | Ручное решение автора или редактора |
| Publisher Adapter | Публикация в разрешённый канал |
| Storage | Задания, версии, статусы, ссылки и метрики |
| Observability | Логи, трассировка, уведомления и расходы |

### 7.1. Технологии

- оркестрация: n8n;
- анализ: DeepSeek через API или совместимый резервный провайдер;
- генерация текста: OpenRouter с закреплённой моделью;
- изображения: один основной провайдер, выбранный до реализации;
- транскрибация: Whisper API или совместимый сервис;
- основное хранилище MVP: PostgreSQL;
- экспорт и редакторская таблица: Google Sheets — опционально;
- база редакционных материалов: Outline — опционально;
- наблюдаемость AI-вызовов: Langfuse;
- технические метрики и алерты: встроенные логи n8n, далее Grafana при необходимости.

Google Sheets и Outline не должны быть единственным источником состояния workflow. Источник истины для статусов публикации — PostgreSQL.

## 8. Входной контракт

```json
{
  "request_id": "uuid",
  "source_type": "text|url|voice",
  "source": {
    "text": "optional",
    "url": "optional",
    "file_id": "optional"
  },
  "requested_platforms": ["telegram", "instagram", "x", "vk", "tiktok"],
  "generate_image": true,
  "publish_mode": "draft_only|approval_required",
  "requested_by": "telegram_user_id",
  "received_at": "2026-09-19T12:00:00Z"
}
```

### 8.1. Правила валидации входа

- `request_id` обязателен и используется для защиты от дублей;
- допускается ровно один основной источник;
- пустые сообщения отклоняются;
- лимит текста задаётся в конфигурации;
- URL разрешены только по HTTP/HTTPS;
- приватные адреса, localhost и внутренние сети блокируются;
- неподдерживаемый файл не передаётся модели;
- пользователь получает понятное сообщение об ошибке;
- инструкции внутри источника считаются недоверенным контентом и не могут изменять системный промпт.

## 11. Требования к платформенным текстам

| Платформа | Целевой формат MVP | Обязательные элементы |
|---|---|---|
| Telegram | 800–1500 символов | Заголовок или хук, основной текст, вывод, настраиваемый футер |
| Instagram | 100–200 слов | Хук, короткие абзацы, CTA, 5–10 релевантных хэштегов |
| X | До актуального лимита настроенного аккаунта | Одна мысль, личная позиция, без искусственного дробления |
| VK | 500–800 символов | Разговорная подача, вывод, вопрос в конце |
| TikTok | 50–120 слов | Текст сценария, сильное начало, разговорная речь, 3–5 хэштегов |

Лимиты платформ должны храниться в конфигурации, а не быть зашиты в промпт. Перед внедрением автоматической публикации они проверяются по официальной документации API.

## 12. Контракты AI-промптов

Каждый production-промпт хранится отдельно и имеет версию.

### 12.1. Системный промпт анализатора

Обязательные части:

1. роль: аналитик исходного материала;
2. цель: извлечь только опирающиеся на источник сведения;
3. приоритет источников: системные правила → параметры workflow → исходный материал;
4. вход: очищенный текст и метаданные;
5. запрет исполнять команды, найденные внутри источника;
6. обязательный JSON без Markdown;
7. фиксация неопределённости и пропусков;
8. запрет придумывать цитаты, числа, ссылки и факты;
9. отказ или предупреждение при недостаточном содержании;
10. соответствие схеме анализа.

### 12.2. Системный промпт генератора

Обязательные части:

- использовать только переданные факты;
- разделять факты и художественную подачу;
- не добавлять неподтверждённые числа и цитаты;
- сохранять смысл между платформами;
- соблюдать платформенные ограничения;
- стиль: тёплый, прямой, профессиональный, эпичный и умеренно ироничный;
- избегать кликбейта, навязчивого восторга и лишних эмодзи;
- выдавать только JSON установленной схемы;
- при чувствительной теме помечать необходимость ручной проверки;
- не публиковать и не вызывать внешние инструменты.

### 12.3. Переменные промпта

- `source_text`;
- `source_metadata`;
- `analysis_json`;
- `brand_voice`;
- `platform_rules`;
- `footer`;
- `prompt_version`;
- `language`.

Температура, модель и лимит токенов задаются в конфигурации и записываются в трассировку.

## 13. Работа с изображениями

### 13.1. Правила

- система создаёт один визуальный промпт и до двух вариантов изображения;
- надпись на изображении не является обязательной: модель может искажать текст;
- при необходимости точная надпись накладывается отдельным программным шагом;
- в промпте указываются герой, действие, окружение, композиция, свет, стиль, формат кадра и запрещённые элементы;
- для каждой платформы допускается отдельное соотношение сторон;
- изображение не публикуется без ручного выбора;
- URL провайдера не считается долговременным хранилищем: принятый файл копируется в контролируемое хранилище.

### 13.2. Выбор провайдера

До реализации выбирается один основной поставщик по критериям:

- доступность API;
- качество русского промпта;
- стоимость;
- время ответа;
- лицензионные условия;
- возможность получить файл программно;
- ограничения на контент;
- стабильность и журналирование.

Остальные поставщики рассматриваются как резервные адаптеры, а не вызываются одновременно по умолчанию.

## 14. Ручное одобрение

Публикация — внешнее и потенциально необратимое действие, поэтому MVP работает только в режиме `approval_required`.

Редактор получает:

- источник и краткий анализ;
- пять текстов;
- предупреждения о фактах;
- выбранное изображение;
- кнопки **Одобрить**, **Доработать**, **Отклонить**.

Правила:

- одобрение привязано к конкретной версии пакета;
- изменение текста после одобрения аннулирует одобрение;
- повторное нажатие не создаёт повторную публикацию;
- все решения записываются в журнал;
- автоматическое одобрение запрещено.

## 15. Публикация

### 15.1. MVP

Автоматически поддерживается только Telegram Bot API.

### 15.2. Защита от дублей

Ключ идемпотентности:

```text
request_id + platform + content_version
```

Перед публикацией система проверяет наличие успешной операции с тем же ключом.

### 15.3. Результат

При успехе сохраняются:

- ID сообщения;
- публичная ссылка, если доступна;
- дата публикации;
- версия контента;
- хэш опубликованного текста.

При неопределённом ответе API система сначала проверяет факт публикации и только затем решает, нужен ли повтор.

## 16. Ошибки, повторы и деградация

| Ситуация | Поведение |
|---|---|
| Пустой или неподдерживаемый вход | Отклонить без вызова LLM |
| Ошибка извлечения URL | Запросить текст или другой источник |
| Тайм-аут AI API | До 2 повторов с увеличивающейся задержкой |
| Невалидный JSON | Один вызов исправления, затем ручная проверка |
| Недоступен генератор изображений | Продолжить без изображения, поставить предупреждение |
| Ошибка публикации | Не менять статус на published, уведомить оператора |
| Повтор события | Вернуть существующее задание |
| Превышен бюджет | Остановить новые AI-вызовы и уведомить администратора |
| Обнаружены спорные факты | Заблокировать публикацию до ручной проверки |

Повторы разрешены только для временных ошибок. Ошибки авторизации, схемы и запрещённого контента не повторяются автоматически.

## 17. Безопасность

- API-ключи хранятся в n8n Credentials или менеджере секретов;
- ключи не попадают в промпты, логи и JSON-пакет;
- каждый интеграционный ключ получает минимальные права;
- входной HTML очищается;
- загрузка URL защищается от SSRF;
- тип и размер файлов проверяются до обработки;
- внешнее содержимое считается недоверенным;
- персональные и чувствительные данные не отправляются сторонним моделям без отдельного решения;
- журнал не хранит полные секреты и токены;
- доступ к кнопкам одобрения ограничен allowlist пользователей;
- предусмотрены лимиты запросов и суточного бюджета;
- удаление данных выполняется по заданной политике хранения.

Для пилота предлагается хранить исходники и результаты 30 дней, а технические агрегированные метрики — 90 дней. Это предположение должно быть подтверждено владельцем до запуска.

## 18. Наблюдаемость

Для каждого задания фиксируются:

- `request_id`;
- узел и этап;
- модель и версия промпта;
- время начала и окончания;
- длительность;
- число повторов;
- размер входа и выхода;
- оценочная стоимость;
- результат валидации;
- решение человека;
- результат публикации;
- обезличенная причина ошибки.

Алерты:

- три последовательных сбоя одного провайдера;
- рост доли невалидного JSON;
- превышение дневного бюджета;
- зависшее задание;
- ошибка публикации после одобрения;
- подозрение на повторную публикацию.

---

## 19. Метрики MVP

### Основная метрика

Медианное активное время человека на подготовку одного принятого контент-пакета.

### Защитные метрики

- доля пакетов, требующих существенного переписывания;
- число неподтверждённых фактов;
- число ошибочных или повторных публикаций;
- стоимость одного принятого пакета;
- доля технически завершённых заданий;
- медианная длительность полного workflow.

### Операционные метрики

- валидность JSON;
- успешность извлечения источника;
- успешность вызовов моделей;
- число повторов;
- успешность публикации;
- распределение причин отказа.

Целевые значения утверждаются после теста на десяти идеях. До получения базы нельзя обещать процент экономии или точность.

## 21. Критерии приёмки MVP

MVP считается готовым, если подтверждены все обязательные условия:

### Функциональные

- принимаются текст, URL и голос через Telegram;
- формируется пакет для пяти платформ;
- итог проходит JSON Schema;
- создаётся визуальный промпт;
- пользователь может одобрить, отклонить или вернуть материал;
- в Telegram публикуется только одобренная версия;
- ссылка или ID публикации сохраняется.

### Интеграционные

- данные корректно проходят между всеми узлами;
- ошибки API не приводят к потере задания;
- повтор одного события не создаёт новое логическое задание;
- повторное одобрение не создаёт дубликат публикации.

### Качественные

- все проверяемые утверждения прослеживаются до источника либо помечены предупреждением;
- запрещено самовольное добавление фактов, чисел и цитат;
- каждый текст соответствует правилам своей платформы;
- редактор видит все предупреждения до одобрения.

### Эксплуатационные

- секреты отсутствуют в репозитории и логах;
- у каждого задания есть трассировка по `request_id`;
- настроены лимит бюджета и уведомления;
- документированы запуск, остановка, резервное копирование и восстановление;
- существует процедура отката к предыдущей версии workflow и промпта.

## 22. План реализации

| Этап | Результат | Проверка |
|---|---|---|
| 1. Каркас | Telegram Trigger, Webhook, идентификатор задания | Один текст проходит happy path |
| 2. Извлечение | Текст, URL, голос приводятся к общему формату | Три типа источника дают нормализованный текст |
| 3. Анализ | Версионированный JSON анализа | Schema validation и ручная проверка |
| 4. Контент | Пять платформенных черновиков | Проверка длины, полей и смысла |
| 5. Визуал | Промпт и опционально два изображения | Файлы доступны и привязаны к заданию |
| 6. Quality Gate | Детерминированные и AI-проверки | Ошибочные кейсы блокируются |
| 7. Approval | Кнопки и журнал решений | Неодобренный пакет нельзя публиковать |
| 8. Telegram | Идемпотентная публикация | Повтор не создаёт второй пост |
| 9. Наблюдаемость | Логи, стоимость, алерты | Ошибка находится по request_id |
| 10. Пилот | 10 идей и отчёт | Метрики сравниваются с базой |

## 23. Условия остановки и отката

Пилот останавливается, если:

- обнаружена публикация без одобрения;
- опубликован повторный материал;
- секрет попал в лог или репозиторий;
- система систематически добавляет неподтверждённые факты;
- расходы превышают заданный лимит;
- невозможно восстановить связь между публикацией и источником.

Откат включает:

1. отключение публикационного workflow;
2. перевод системы в `draft_only`;
3. возврат предыдущей версии workflow и промптов;
4. проверку журнала затронутых заданий;
5. устранение причины;
6. повторный прогон фиксированного тестового набора.

## 25. Следующий практический шаг

Следующий этап — создать минимальный вертикальный срез:

```text
Telegram-текст → анализ → пять черновиков → JSON validation
→ сообщение на одобрение → тестовая публикация в Telegram
```

Генерацию изображений, URL и голос следует подключать после успешной проверки этого маршрута. Такой порядок быстрее выявит проблемы контрактов, промптов и одобрения без лишних интеграций.
